# Spec: Internationalisation (i18n)

**Status:** Done (one PR for all parts, by the maintainer's choice) · **Milestone:** none yet (backlog) · **Design:** `docs/design/frontend.md` §5.4 (appearance, the closest per-user setting)

## Goal

An admin picks a language in Settings and the whole web UI appears in it, with dates, numbers and sizes formatted for that language. English stays the default and the fallback. It is for non-English-speaking home-server owners and for contributors who want to add a language with one JSON file.

## Non-goals

- Translating the assistant's replies, server log lines, audit entries, catalog app descriptions or the docs/website (the assistant answers in the user's language by itself).
- Right-to-left layout (a later spec).
- A translation-management service. Strings live in the repo.
- Machine-translating every language up front. Ship English plus one or two reviewed languages.

## Platforms

Host-independent: no capability id. The language is a per-user preference like appearance. Server error messages that reach the UI stay English at first (see open questions).

## Design

- **Web:**
  - Library: `next-intl` is built around the App Router and server rendering; with `output: "export"` and no dynamic `[locale]` routes it is awkward. Use **`react-i18next` + `i18next`** (client only, no routing change), or a ~100-line own `useT()` over JSON. Recommendation below.
  - Messages: `apps/web/locales/<lang>/<area>.json`, one namespace per `components/<area>` folder, keys like `store.install.title`. English is the source of truth; its keys generate the type, so `t("typo")` fails `pnpm typecheck`.
  - Plurals use i18next's own forms (`key_one`, `key_other`) and interpolation `{{name}}` (no ICU plugin, no extra dependency); no string concatenation. Markup inside a sentence uses `<Trans>`.
  - Language detection order: saved user preference, `navigator.language`, `en`. Before sign-in (`/login`, `/setup`, `/s/`) only the browser language and `localStorage` apply.
  - A tiny inline script (like `APPEARANCE_SCRIPT`) sets `<html lang>` before paint. Locale files load per page (dynamic import) so the bundle doesn't grow with every language.
  - `lib/format.ts` (dates, sizes, numbers) takes the locale from the same provider and uses `Intl`; the raw `toLocaleString()` calls (e.g. in the backup list) go through it.
  - Settings → Appearance gets a Language select (names written in their own language).
- **Server (as built):** `language` is a field of the appearance JSON (`users.appearance`), `"auto"` by default, checked by pattern like the other ids; no migration. `GET/PUT /api/settings/appearance`; `pnpm gen:api`.
- **Assistant / MCP:** none. The system prompt gets the user's language as a hint.
- **Security:** the language is validated against the list of shipped locales; never used in a path.
- **Dependencies:** `i18next`, `react-i18next` (both MIT), recorded in `docs/design/licenses.md`.
- **Guards:** `scripts/check-i18n.mjs` (run from `scripts/check.sh web`): every language has exactly English's keys and placeholders, no unused keys. ESLint rule or check that flags new hard-coded JSX text in `components/`.

## Parts

1. **Foundation** — provider, `useT`, typed keys, `<html lang>`, language setting (server column, API, Settings select), formatters on `Intl`, check script, English catalogue for the shell only (nav, header, login, setup, Settings). One extra language to prove the path. Browser-verified at phone width and both themes.
2. **Move the strings** — one PR per area group (dashboard + apps; store + files; containers + packages + terminal; cloud + automation + assistant + settings). Mechanical: extract text, no behaviour change.
3. **Languages** — add reviewed translations (which ones: see questions) and a `docs/` section on adding a language.

## Acceptance checks

- Unit: key-parity script fails when a key or placeholder is missing; plural forms render for 0, 1, many; fallback to English for a missing key.
- Server: `language` round-trips; an unknown code is rejected (422); migration upgrades and downgrades.
- Browser (`athena-ui-verify`): switch language in Settings, reload, the choice persists; `<html lang>` changes; no English left on the shell pages; long German/Portuguese strings don't overflow buttons or the sidebar at phone width.
- Unsigned pages follow the browser language.

## Open questions

- Library — recommendation: `react-i18next`. It works on a static export with no routing change and has ICU plurals via a plugin, instead of `next-intl`, which wants `[locale]` routes.
- First languages — recommendation: English plus Portuguese (Brazil), the maintainer's language, so you can review it. Others later via PRs.
- Server error text shown in toasts — recommendation: leave English in part 1; later return stable error codes from the API and translate them in the UI.
- Where the choice lives — recommendation: per user (server) with a `localStorage` copy for pre-login pages, same as appearance.
- Enforce "no hard-coded text" — recommendation: a lint rule (`eslint-plugin-i18next`, MIT) only after part 2, so it doesn't block the migration PRs.

## As built

- `apps/web/lib/i18n/` (init, `LANGUAGES`, `setLanguage`, `currentLocale`), `components/i18n-provider.tsx`, `locales/<lang>/<namespace>.json`, `scripts/check-i18n.mjs` (key and placeholder parity, part of `scripts/check.sh web`).
- Screen-reader labels inside shared `packages/ui` components (dialog and sheet close, sidebar toggle) come from `UiLabelsProvider` (`packages/ui/src/lib/ui-labels.ts`), filled by `I18nProvider`.
- Browser-verified in Portuguese (pre-login pages, every sidebar page, phone width, dark mode, number/date formats). Not verified: populated pages (apps, containers, cloud remotes, backups, store, assistant chat), a real pt-BR browser locale, a native-speaker review of the Portuguese.
- Not done (still in the spec's non-goals or follow-ups): translating server error messages (stable error codes first), the hard-coded-text lint rule (`eslint-plugin-i18next`), more languages and a doc on adding one.
